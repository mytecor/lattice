# Детекция повторных (зацикленных) ответов модели как отдельное routing-правило

Фича: [F7 — LLM gateway](./README.md). Относится к подсистемам typed routing rules
([rule.go](../../packages/llm-gateway/rule.go), [rule_continue.go](../../packages/llm-gateway/rule_continue.go)),
релейному streaming-циклу [server.go](../../packages/llm-gateway/server.go) и
takeover-механизму [router_stream.go](../../packages/llm-gateway/router_stream.go).

**Статус: реализовано (релейный цикл + Nix-подключение + тесты Go/Nix готовы).**

Состояние проверки на момент реализации: полный Go-набор зелёный (`go test ./...`), включая
детектор, правило, integration-стримы и метрику; Nix-контракт sugar (opt-in, явные поля, clean
JSON) проверен фактической generate-оценкой модуля — на модели с `repetition.enable = true`
эмитируется `{"action":"repetition","min_len":8,"repeats":5,"route":"smart"}` (null-поля
опущены), на не-opt-in модели действия нет ровно как раньше. Полный чек
`checks.x86_64-linux.llm-gateway-sugar` собирается на Linux-билдере (здесь `aarch64-darwin`
собрать нельзя), поэтому он выполняется в CI/на ноде.

## Решение (зафиксировано при реализации)

Действие названо `repetition` (конвенция F7 — одно слово-существительное). Оно
объявляется на entry-route рядом с `continue` и является чисто **опциональной
политикой**: отсутствие правила означает «детекции нет» (ровно как у `continue`).

- **Порядковый детектор** («N-й подряд идентичный нормализованный фрагмент»):
  accumulated-хвост нормализуется (нижний регистр, схлопывание пробелов и
  пунктуации `. , ! ? ; : " '` в один разделитель, в т.ч. через границы чанков) и
  сравнивается на повтор K+ подряд одинаковых фрагментов длины в
  `[MinLen, MaxLen]`. Минимальный фрагмент строго >= `MinLen`: повтор коротких
  слов/барьерных символов (`ha`, `yes`, `}`, ...) — это связная речь/нумерация, а
  не зацикленность, и он не срабатывает. Хвост ограничен `MaxLen*Repeats`, так что
  стоимость на событие `O(MaxLen*Repeats)` без роста от длины turn.
- **Опциональность**: детектор кормится извлечённым текстом чанка
  (`streamTextDelta`, content + reasoning), а не сырым SSE-JSON с его служебной
  пунктуацией. На моделях без правила `repetition` релейный цикл ведёт себя как
  раньше (регрессия существующих тестов чистая).
- **Порог по умолчанию**: `Repeats=4`, `MinLen=6`, `MaxLen=256` — безопасный
  дефолт, не трогающий нормальные длинные ответы (в т.ч. GLM reasoning-only-кейс из
  [continue.go](../../packages/llm-gateway/continue.go)).
- **Стоп + continue**: при срабатывании порога стрим останавливается **без
  ретрансляции** сработавшего чанка, обрыв помечается `RecordStreamFailure` (провайдер
  уходит в cooldown) и идёт существующий `ContinueStream` с накопленным `partial`
  (`appendPartialChatHistory`) — тот же путь, что у stall/`no finish_reason`.
  `swapTo` при приёме нового вуннера **сбрасывает детектор**, чтобы продолжение не
  было немедленно пере-трипнуто хвостом зацикленного накопителя.
- **Защита от рецидива**: повторный продолженный стрим снова проходит детектор, но
  цепочка ограничена существующими `maxContinueChainRetries`/`Wait` — в бесконечный
  цикл continue→повтор→continue не входит. Когда продолжение невозможно (нет
  доступного провайдера), срабатывает существующий терминальный error-contract
  `upstream stream failed`.
- **Метрика/событие**: `llm_repetition_detected_total{route,provider}` — ровно один
  инкремент на детекцию (не на фрагмент); structured event `llm_repetition_detected`.

## Контекст

Наблюдение на ноде (24.09.2026, сессия pi-acp `hydra_session_x4VnUba7joi3ucZP`) и в прямом
pi без pi-acp: модель `standard` (DeepSeek-V4-Flash-0731 через llm-gateway) входит в состояние
**самоповтора** — начинает бесконечно повторять один и тот же фрагмент вывода. В зацикленной
сессии это выглядело как `Tool call.` ×тысячи с нулевыми реальными tool-вызовами и без
`finish_reason` в течение ~27 минут; контекст сессии при этом вырос с 14k до 61k токенов
(раздутие за счёт повторяемого текста, попадающего в следующий запрос). Проблема воспроизводится
и без pi-acp, т.е. источник — pi-рантайм и/или модель, а не транспорт (`pi-acp`/`acp-normalizer`
только склеивают messageId и не фильтруют повтор).

В llm-gateway уже есть механизм **continue** (`ActionContinue`, rule `continue`) — при обрыве
стрима (нет данных / нет `finish_reason` / stall watchdog) он перезапрашивает с накопленной
историей через `ContinueStream`. Но это **зашитое ядровое поведение**, и оно реагирует только
на обрыв, а не на **содержательный повтор** (модель ответила дважды одинаково и не завершает
turn). Такой стрим идёт клиенту до бесконечности, жжёт output-токены и раздувает контекст.

**Требование (из запроса):** детектор повторов должен быть **отдельным routing-правилом,
которое можно опционально подключать** на нужные логические модели, а не частью ядра
llm-gateway. Это совпадает с архитектурой F7: routing actions живут как отдельные типы в
`ruleRegistry`, валидируются и применяются через `apply`, подключаются на entry-route; ядро
не получает зашитой логики, а только вызывает опциональную политику.

## Что сделать

- [x] **Новое routing-действие `repetition`.** Добавить
      в [rule.go](../../packages/llm-gateway/rule.go): константу `ActionRepetition`,
      дескриптор в `ruleRegistry` (рядом с `continue`, rank 14), новый файл
      `rule_repetition.go`. Правило **никогда не включается по умолчанию** — отсутствие правила
      на route означает «детекции нет», ровно как у `continue`.
- [x] **Типизированная конфигурация правила.** По аналогии с `ContinueRule`: `Repeats`, `MinLen`,
      `MaxLen` (без `enabled` — само наличие правила на entry-route включает детекцию); `apply`
      валидирует (repeats ∈ [2,100], minLen ≥ 2, minLen < maxLen, maxLen ≤ 1024, требует entry
      route + предшествующий `race`) и пишет в `compiledRoute.Repetition`. Минимум порога — чтобы
      не срабатывать на естественных повторениях слов в связной речи и на документально
      известных «reasoning`only, 0 content»-кейсах.
- [x] **Точка вызова в релейном цикле — только через политику, без зашитой логики.**
      В [server.go](../../packages/llm-gateway/server.go) читается опциональная политика
      `repetition` (`repDetector`); если политики нет — релейный цикл ведёт себя как сегодня.
      Если есть — проверка повтора как ещё одно условие «стоп → continue», наравне с
      idle/нет-finish_reason. Реализация детектора живёт в `repetition.go`, не в `server.go`.
- [x] **Детектор как самостоятельный компонент.** `repetition.go`: нормализация (нижний регистр,
      схлопывание пробелов/пунктуации `. , ! ? ; : " '`, терминирование через границы чанков),
      bounded-хвост, сравнение порядкового повтора. Unit-тесты в `repetition_test.go`.
- [x] **Стоп + перезапрос с историей через существующий continue.** При срабатывании порога:

- [x] **Метрики/события.** `llm_repetition_detected_total{route,provider}` (ровно +1 на

- [x] **Пример подключения и документ.** `pipeline.repetition = { enable, repeats, minLen, maxLen };`

## Открытые вопросы → решения

- **Имя действия:** выбрано `repetition` (одно слово-существительное, конвенция F7 —
  `filter/map/rank/...`; rank 14 в `ruleRegistry`). `loop_guard`/`guard_loop` отклонены для
  единообразия с `continue`.
- **Что считать «повтором»:** реализован **порядковый** детектор — N-й подряд идентичный
  нормализованный фрагмент длины `[MinLen, MaxLen]` (не накопленный текст последних L символов).
  Проще, не даёт ложных срабатываний на связной речи и покрывает «Tool call.»-кейс. Накопленный
  режим не вводится (YAGNI); при необходимости расширяется позже в том же `RepetitionConfig`.
- **Взаимодействие с `finish_reason`:** нормальный финиш повтор не останавливает — срабатывает
  только «не закрывающийся» стрим, продолжающий дублировать один фрагмент до `finish`.
- **Порог по умолчанию:** `Repeats=4`, `MinLen=6`, `MaxLen=256`. Не трогает нормальные длинные
  ответы (в т.ч. GLM reasoning-only-кейс из [continue.go](../../packages/llm-gateway/continue.go));
  минимальный фрагмент строго ≥ `MinLen` защищает от ложных срабатываний на связной речи
  (`ha`, `yes`, `}`, ...). Верхние пределы валидации: repeats ≤ 100, maxLen ≤ 1024.
- **Стоп для клиента:** loop-guard останавливает стрим **без `[DONE]` и без error-фрейма**, когда
  возможно продолжение (winner-чтимирование + continue): клиент просто видит обрыв повтора и
  продолжение там, где кончился повтор. Терминальный error `upstream stream failed` (без `[DONE]`)
  срабатывает **только** когда продолжение невозможно (нет unused-провайдера) — и тогда повторный
  retry остаётся на стороне клиента (`pi-retry`), как и для остальных терминальных обрывов.
