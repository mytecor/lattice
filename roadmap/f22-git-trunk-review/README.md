# F22. Git review и trunk

Контролируемое принятие результатов задач в `main`: рабочие ветки, независимый reviewer,
отдельные checks и один итоговый коммит задачи. Хранилище кода и ценных review-метаданных — Git.
Сервис принятия не знает структуры фич и задач; Radicle — сменяемая репликация, а не обязательный
review backend.

Соответствует [вехе 22](./../../ROADMAP.md#f22-git-review-и-trunk). Требования — в
[AGENT_WORKFLOW.md](./../AGENT_WORKFLOW.md#git-review-и-принятие).
Использует контейнеры [F10](./../f10-disposable-worker/README.md); распределённая приёмка
проектируется совместно с [F23](./../f23-distributed-coordination/README.md).

**Статус:** реализация не начата; план уточнён 2026-11-03. Первым проверяется готовый Gerrit.
Собственный `merged` рассматривается при воспроизводимом несоответствии требованиям или
чрезмерной сложности адаптации. До ADR backend не выбран; параллельные review-системы не создаются.

## Согласованная модель

- На каждой физической ноде свой сервис; принятый `main` един для всех. F23 согласует переход
  от ожидаемого SHA к точному итоговому SHA. Копии могут отставать, но не принимать другую вершину.
  Без большинства новые принятия ждут; локальный merge не является окончательным принятием.
- Radicle реплицирует Git-объекты и необходимые refs. Общий адрес репозитория не считается
  общей атомарной точкой push. Контракт не зависит от Radicle review или выбора canonical refs.
- Агент публикует ветку обычным Git. Для Gerrit интеграция готовит один коммит задачи;
  исправления загружаются patch sets, рабочая история и checkpoints сохраняются отдельно.
- Review и checks идут через интерфейс Lattice. Сервисы нод проверяют согласованные F23
  назначения и выдают ограниченные полномочия; долговременные credentials Gerrit остаются
  на хостах. Отдельная служба выдачи не требуется.
- Только системный путь принятия обновляет `main`. Устаревший кандидат переносится на новый
  trunk; конфликт возвращается агенту. Изменённый кандидат снова проходит review и checks.
- Gerrit проверяется с общим слоем F23. Отдельный multi-site стек не является обязательным;
  наличие validation hook само по себе не доказывает корректность распределённого принятия.

## Критерий готовности

- Агент локально работает обычным Git, публикует предложение, но не пишет прямо в `main`.
  Reviewer действует через интерфейс Lattice с отдельными ограниченными полномочиями;
  самоодобрение не принимается.
- Approval передаётся операцией над конкретной версией кандидата и сохраняется в Git вне файлов
  задач. Checks публикуются независимым исполнителем; review не теряется при смене репликации.
- Кандидат переносится на актуальный trunk автоматически; конфликт возвращается автору.
  Изменение кода требует новой проверки, одни служебные коммиты задач не вызывают бесконечного
  сброса approval. В `main` оказывается проверенный результат задачи одним коммитом.
- Права публикации состояния и делегирования проверяет интеграция Lattice, не универсальное
  Git-ядро. Политику репозитория меняют только после подтверждения человека.
- Локальная атомарность bare ref и межнодовое согласование различены и испытаны совместно с F23.

## Открытые решения

Выбор backend, механизм выдачи и отзыва ограниченного доступа, привязка прав reviewer к change,
хранение checks, определение exact candidate, автоматическое принятие служебных изменений и распределённое
развёртывание. Вариант Gerrit требует оценить его аккаунты, ACL, NoteDb и HA, а не считать его
обычным stateless hook поверх независимо реплицируемых bare-репозиториев.
