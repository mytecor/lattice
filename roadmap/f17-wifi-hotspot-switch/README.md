# F17. Динамический режим ноды: Ethernet-uplink → Wi-Fi становится точкой доступа

Нода Lattice — **многодомная** (проводной `enpX` + Wi-Fi `wlp*`, см. модель в
[`profiles/tcp-gateway/config.nix`](../../profiles/tcp-gateway/config.nix#L52-L58)). Wi-Fi-радио на
железе (Realtek RTL8822CE, драйвер `rtw88_8822ce`) умеет работать **либо как клиент (STA), либо
как точка доступа (AP), но нестабильно одновременно на одном канале** — зафиксировано живым
тестом в снятом модуле `wireless-hotspot` (см. ниже). Поэтому возникает задача: **когда нода
выходит в интернет по проводу (Ethernet), выключать Wi-Fi-клиента и переводить радио в режим
точки доступа** («хотспот»), чтобы ноду можно было использовать как маршрутизатор/точку входа
для соседних устройств. При отключении кабеля — возвращаться обратно в клиентский режим.

Соответствует будущей вехе в [ROADMAP.md](../../ROADMAP.md#f17-аварийный-доступ-и-хотспот).

## Зачем

- Нода по проводу имеет прямой интернет; её Wi-Fi-радио при этом **простаивает** в режиме клиента
  (например, подключено к домашнему AP). Это расточительство: радио можно использовать как
  независимую точку доступа для локальных устройств.
- Обратный кейс — «аварийный доступ»: если нода живёт в полевых условиях и единственный канал
  наружу — Ethernet (например, спутниковый/кабельный модем), то Wi-Fi должен раздавать сеть
  клиентам, а не пытаться подключиться к отсутствующему AP.
- На многодомной ноде режим точки доступа даёт физически отдельный L2-сегмент, не зависящий от
  того, в какой сети сидит проводной аплинк.

## Ключевой факт из доков (запись теста)

В git-истории есть зафиксированный результат живой проверки — снятый модуль
[`modules/wireless-hotspot`](https://github.com/mytecor/lattice/commit/0e25850) (реализация
**одновременного** STA+AP на одном радио) и его отключение `009976b` + удаление `26be494`. Из
README снятого модуля:

> Модуль у `rtw88_8822ce` только один радио-канал:
> ```
> valid interface combinations:
>        * #{ managed } <= 1, #{ AP } <= 1,
>          total <= 2, #channels <= 1
> ```
>
> Это накладывает три обязательных ограничения:
> 1. AP-интерфейс создаётся с уникальным MAC (не MAC STA-интерфейса).
> 2. AP работает в простом формате 802.11n (HT), даже на 5 GHz; VHT (802.11ac) на этом железе
>    нестабилен.
> 3. **Канал AP обязан совпадать с каналом STA** — `#channels <= 1`, переключение радио оборвёт STA.
>
> Точка доступа на `rtw88_8822ce` работает **только при STA на 2.4 GHz**. Как только STA уходит
> на **5 GHz**, concurrent AP ломается во всех проверенных режимах (VHT20 рвёт data path,
> VHT80 валит hostapd, HT20 — клиент не ассоциируется). Рабочий вариант требует **отдельного
> Wi-Fi-радио** для AP.

**Вывод для нашей задачи:** одновременный STA+AP на этом чипе — тупик. Но наша задача не требует
одновременности. **F17 переключает режим целиком:** провод есть → Wi-Fi работает ТОЛЬКО как AP
(STA выключен, канал свободен, `#channels <= 1` не мешает, т.к. клиентского линка нет вообще);
провода нет → Wi-Fi возвращается в клиентский режим. Это обходит ограничение снятого модуля.

## Что реализуем

### Модуль `modules/hotspot-switch` (новый, вместо снятого `wireless-hotspot`)

Динамический systemd-механизм, который следит за состоянием проводного аплинка и переключает
режим Wi-Fi-радио. Логика детерминированная, состояния конечны:

| Состояние | Ethernet-аплинк | Wi-Fi-радио |
|---|---|---|
| `client` (дефолт) | нет (или не default-route) | STA через NetworkManager (текущая `lattice.wireless`) |
| `ap` (hotspot) | есть проводной аплинк с интернетом | hostapd AP на `ap0`, dnsmasq DHCP, NAT наружу |

Триггер — watch-механизм (не периодический поллинг): `systemd.path` на состоянии кабеля +
событийный хук NetworkManager. Следить надо за **наличием проводного аплинка с default-route в
интернет**, а не просто «кабель вставлен» (иногда провод есть, а интернета по нему ещё нет).

### Опции модуля (черновик)

```nix
lattice.hotspot-switch = {
  enable = false;
  ethInterfaces = [ "enp3s0" ];       # какие провода считать аплинком (candidate default-route)
  wifiInterface = "wlp2s0";           # STA-интерфейс, которым управляет NetworkManager
  ap = {                              # по сути — опции снятого wireless-hotspot (ssid/пароль/подсеть)
    ssid = "...";
    passwordFile = "...";             # agenix secret (hotspot-password.age уже есть)
    ip = "10.44.0.1/24";
    dhcpRange = "10.44.0.10,10.44.0.100,255.255.255.0,12h";
    # канал/полоса теперь свободны: STA выключен → можно фиксировать, не подстраиваясь под STA
    channel = 36;  hwMode = "a";
  };
};
```

### Механика переключения

**Вход в AP-режим** (появился Ethernet default-route):
1. Остановить NetworkManager Wi-Fi-профиль (`nmcli device disconnect $wifi`), перевести интерфейс
   в unmanaged.
2. `iw phy phy0 interface add ap0 type __ap` с уникальным локально-администрируемым MAC (требование
   драйвера, см. снятый модуль).
3. Поднять hostapd (+ сгенерировать `hostapd.conf` из age-секрета), dnsmasq на `ap0`, NAT/MASQUERADE
   наружу через проводной аплинк, FORWARD-правила.
4. Служебный интерфейс-состояние записывается в `/run/lattice-hotspot-switch/mode`.

**Выход из AP-режима** (Ethernet пропал / потерял default-route):
1. Остановить hostapd, dnsmasq, удалить `ap0`.
2. Вернуть интерфейс в managed, NetworkManager сам переподключит известный Wi-Fi-профиль
   (`autoconnect-priority` из `lattice.wireless` уже ранжирован).

### Надёжность

- `systemd.path` (`PathExists`/`PathChanged`) на `/sys/class/net/$eth/carrier` + `NetworkManager`
  Dispatcher script (события `up`/`down`/`address-change`) для реального default-route.
- Идемпотентность: переходы — one-shot юниты с `RemainAfterExit`, повторный вход/выход — no-op.
- Гонки (кабель выдернули в момент входа в AP): таймаут и повторная оценка состояния; AP не
  поднимается, пока нет подтверждённого проводного default-route.
- Rollback при сбое: если hostapd не поднялся, вернуться в `client` и оставить Wi-Fi в managed.
- **Блокировка одновременности:** assertion/программная проверка, что в AP-режиме STA-профиль не
  активен, а в client-режиме `ap0` не существует — иначе воспроизведём нестабильность снятого модуля.

## Примечание по снятому модулю

Старый `modules/wireless-hotspot` умел **одновременный** STA+AP и был удалён, потому что на этом
железе это нестабильно (см. выше). Возрождать его не надо: F17 делает **переключение**, а не
одновременность. Одновременный STA+AP — осознанно откладываемая производная, требующая отдельного
второго Wi-Fi-радио.

**Критерий готовности:** на многодомной ноде с вставленным проводом Wi-Fi раздаёт клиентам
интернет через hostapd/dnsmasq/NAT; после выдёргивания провода нода возвращается в Wi-Fi-клиентский
режим; в любой момент активно ровно одно состояние (STA **или** AP), одновременного линка нет;
переходы переживают гонки кабеля и не требуют ручных действий.

**Осознанно откладываем (до F…):** одновременный STA+AP на одном радио (нужно второе радио —
USB-адаптер) — отложено навсегда, пока нет второго радио; агрегация/предпочтение между проводным и
Wi-Fi аплинками для общего интернета — отдельная задача маршрутизации; интеграция с F11 controller.
