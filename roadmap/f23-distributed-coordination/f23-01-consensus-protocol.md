# Выбрать и проверить протокол координации

Фича: [F23](./README.md). Связанные границы: [runtime F19](./../f19-agent-execution-loop/README.md),
[trunk F22](./../f22-git-trunk-review/README.md), [исполнение F21](./../f21-multi-agent/README.md).

## Что сделать

- [ ] Выбрать готовую основу консенсуса, проверить адаптацию транспорта к RNS/meshbus,
      поведение при потерях/перестановках сообщений, хранение журнала и восстановление.
- [ ] Определить начальный состав из identity конфигурации, admission разрешённых нод,
      догоняющее состояние и безопасную смену состава. Принадлежность realm не считать правом голоса.
- [ ] Задать политику автоматического исключения при длительной недоступности; проверить,
      что решение требует текущего большинства и не создаёт двух независимых составов.
- [ ] Определить минимальный API прав исполнения для `agentd`: согласование конкурентных
      запусков, действительность полномочий и отказ от продления run при потере права.
- [ ] Проверить взаимодействие с существующим r1s lease: последний подтверждённый срок,
      продление с задержкой, потеря связи, зависание/рестарт `r1sd`, граница передачи права
      и отклонение устаревших публикаций. Не добавлять task semantics в r1s.
- [ ] С F22 выбрать протокол единого принятого `main` при сервисе на каждой физической ноде:
      согласовать ожидаемый SHA → точный итоговый SHA, без большинства принятия ждут.
      Копии могут отставать, но не принимать независимые вершины. Отдельно разобрать согласование SHA,
      доступность Git-объектов, локальный bare CAS и восстановление после частичного выполнения.
      Кворум назначения не считать автоматически решением принятия Git-изменений.
- [ ] Определить границу авторизации и выдачи credentials reviewer: кто выдаёт, что подписывает,
      область прав, отзыв и проверка принимающим сервисом. Выдают доверенные сервисы нод по
      согласованным назначениям; отдельная служба выдачи не нужна. Review/checks идут через
      интерфейс Lattice, долговременные credentials Gerrit остаются на хостах.
- [ ] Зафиксировать ADR, модели отказов и дальнейшие задачи реализации. Решение должно сохранять
      заменяемость Radicle и не вводить отдельное авторитетное хранилище review.

## Критерий готовности

- [ ] PoC на трёх нодах, разделение 2+1, потеря/возвращение владельца, рестарт участников и
      отсутствие большинства показывают согласованное поведение без потери Git-задач.
- [ ] Рост 1→2→3 и исключение ноды не обходят требования большинства.
- [ ] Документировано, какие решения сохраняет консенсус, какие данные восстанавливаются из Git
      и что гарантируется при невозможности подтвердить остановку старого runtime.
