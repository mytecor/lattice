## Фичи, задачи и память

- Фича описывает цель и критерии принятия и объединяет задачи в том же репозитории, где
  меняются код и документация. Отдельная ветка фичи не нужна: рабочие ветки создаются под задачи.
- У каждого агента, включая руководителя, planner, docs и reviewer, своя логическая задача.
  Иерархия агентов выражена иерархией задач: `parent` задаёт подчинение и путь эскалации,
  зависимости отдельно задают порядок выполнения. Runtime ID агентов, контейнеров и ACP-сессий
  в файлах задач не хранятся.
- Файл задачи содержит поручение и сжатую рабочую память: контекст, прогресс, проблемы и итог.
  Новый исполнитель продолжает ту же задачу; отдельный файл на каждый перезапуск не требуется.
- Рабочее состояние размещается в `.tasks/` с группировкой по фичам по образцу текущего
  [roadmap](./../ROADMAP.md). Точные имена файлов и схема контракта будут определены в F20.
- Успешные задачи остаются в составе открытой фичи, чтобы сохранялись зависимости и контекст.
  После итогового принятия фичи её рабочие файлы удаляются из актуального дерева. Постоянный
  результат — код и документация; история работы остаётся в Git. Ошибка или блокировка не
  являются причиной удаления задачи.

## Постановка и автономность

1. Root — агент, через которого человек обсуждает потребность. Он сохраняет сжатый драфт
   незаконченного обсуждения в отдельной опубликованной ветке; следующая сессия может его загрузить.
2. Только явная команда человека переводит драфт к выполнению. До неё planner и исполнители
   автоматически не запускаются.
3. Отдельный planning-агент строит фичу, иерархию задач, зависимости и критерии принятия.
   Review-задачи создаёт система по фиксированной политике, а не произвольное назначение автора.
4. После запуска система работает независимо от сессии root. `git-watchd` на физических нодах
   сообщает об изменениях через meshbus; `agentd` сверяет Git-состояние и запускает каждый
   готовый узел, а не требует постоянно работающего root.
5. Зависимость разблокируется после принятия результата предшественника в `main`, а не после
   одного approval или успешного локального теста. При старте и восстановлении выполняется
   повторный обход текущих задач; пропущенное уведомление не должно терять работу.

Root может менять цель и исходные критерии фичи только по решению человека. Руководитель может
менять декомпозицию своего поддерева, роли и зависимости в пределах поручения, сохраняя внешние
обязательства. Изменение ожидаемого результата поднимается выше.

## Границы компонентов

| Компонент | Целевая ответственность |
| --- | --- |
| `taskd` | CLI рядом с агентом в каждом контейнере; чтение, валидация и изменение файлов задач. Без Git push, запуска контейнеров и распределённой оркестрации. |
| Агент | Локальная работа обычным Git, коммиты и публикация рабочей ветки в специальный remote. Задачи изменяет через `taskd`, который владеет их форматом. |
| `agentd` | Сверка готовых задач, запуск и сопровождение исполнителей, новые сессии руководителей при эскалации. Экземпляры работают на разных нодах. |
| `git-watchd` | Наблюдение за Git-ревизиями без знания формата задач; уведомления через meshbus. |
| r1s / `r1sd` | OCI-контейнеры, размещение и runtime lifecycle, включая существующий lease. Задачи, фичи и reviewer ему неизвестны. |
| meshbus / RNS | Аутентифицированная связь сервисов и уведомления. Уведомление само по себе не является назначением или правом принятия. |
| Git trunk/review | Приём предложений, аутентифицированные review и checks, rebase и контролируемое принятие в `main`; без знания устройства задач. Gerrit или собственный `merged` — открытый выбор F22. |
| Слой координации | Отдельный распределённый слой согласования на физических нодах; протокол и точный API предстоит выбрать в F23. |

Первая версия не требует A2A или прямого ACP/MCP-взаимодействия между исполнителями. ACP служит
для управления сессией агентом со стороны runtime; долговременные поручения, вопросы и результаты
передаются через Git. Дочерняя работа не ограничивается временем жизни сессии родителя.

## Git, review и принятие

- Основа — обычные Git-репозитории. Radicle является сменяемым механизмом репликации, его
  patches/review/COB не должны быть обязательным контрактом процесса. Review-метаданные тоже
  должны храниться в Git вне файлов задач; отдельное авторитетное хранилище review не требуется.
- Агент свободно работает локальным Git и публикует ветку задачи в специальный remote. Прямая
  запись агентскими credentials в принимаемый `main` запрещена на стороне приёма.
- При собственном `merged` сервис работает с bare Git-репозиторием и не зависит от Radicle.
  Приём предложений локален на каждой ноде, отдельного кворума сохранения рабочей ветки на push
  не требуется. Успех такого push подтверждает локальное сохранение; межнодовая репликация —
  отдельный шаг, а не неявная гарантия сохранения на большинстве.
- Прогресс, вопросы и память публикуются отдельными от кода коммитами. Допустимые изменения
  своего состояния принимаются автоматически; planner и руководители также делегируют и меняют
  задачи в пределах своих полномочий. Знание этих правил остаётся в интеграции Lattice, а не
  в универсальном Git-сервисе.
- Обычная задача требует одного независимого reviewer и независимого проверочного запуска.
  Минимум проверок задаётся принятой политикой репозитория, задача может добавлять требования.
  Кандидат не может сам ослабить действующую политику.
- Approval передаётся отдельной аутентифицированной операцией и относится к точному кандидату.
  Поле в файле задачи, Git author и самостоятельно объявленная роль не предоставляют права.
  Reviewer получает отдельные ограниченные полномочия; самоодобрение запрещено. Удостоверения
  выдают доверенные сервисы физических нод на основании согласованных F23
  назначений. Review/checks агент передаёт через интерфейс Lattice; сервис проверяет полномочия
  и записывает решение в backend. Долговременные credentials Gerrit остаются на хостах;
  отдельная служба выдачи не требуется. Точный механизм выдачи и отзыва ещё проектируется.
- Замечания возвращаются автору в ту же задачу; исправления создают новую версию кандидата.
  Сервис сначала пробует автоматический rebase на актуальный `main`. При конфликте сообщает
  агенту причину, сохраняя предложенную работу; после уже подтверждённого push это результат
  обработки предложения, а не задним числом отказ Git-транзакции.
- Изменившийся кодовый кандидат проходит необходимые проверки и повторное review. Одни только
  служебные обновления задач не должны обнулять approval, если код, постоянная документация,
  требования и политика принятия не изменились. Точный способ определения кандидата — часть F22.
- Результат задачи попадает в `main` одним коммитом. В варианте Gerrit нужно учесть модель
  «один change — один commit»: локальную рабочую историю собирают до загрузки review-кандидата,
  а его обновления публикуют patch sets. Автоматический squash произвольной ветки Gerrit не
  считается уже предоставленной возможностью.
- Docs-агент имеет отдельную задачу на фичу, может готовить материалы заранее и сверяет их с
  фактической принятой реализацией. Отдельный reviewer фичи проверяет интеграцию, документацию
  и исходные критерии после принятия задач в `main`.
- Провал итогового review оставляет фичу открытой: создаются или переоткрываются задачи
  исправлений. Уже доступное проблемное поведение временно отключается по заранее описанному
  безопасному плану; при отсутствии безопасного способа вопрос поднимается до человека.
- Изменение политики репозитория требует подтверждения человека через root. Истечение
  credentials не должно уничтожать уже принятое проверяемое свидетельство review.

## Проблемы и управление работой

Проблема записывается в задаче и поднимается непосредственному родителю. `agentd` при необходимости
создаёт новую сессию руководителя с сохранённой памятью. Каждый уровень решает вопрос в своих
пределах или обобщает его для следующего: детали реализации не должны без обработки попадать
к руководителю фичи или человеку. Вопрос человеку сохраняется до следующего обращения к root,
немедленный внешний канал уведомлений не обязателен. Независимые ветви работы продолжаются.

Жёсткого универсального лимита циклов исправлений/review нет: исполнитель продолжает работу до
явной блокировки и эскалации. Это не отменяет необходимости отдельно определить технические
границы одного runtime-запуска и условия живости процесса.

- **Пауза:** агенты прекращают основную работу, публикуют checkpoints и сжатую память и
  завершаются. Новые запуски и принятие изменений фичи остановлены; сохранение при паузе разрешено.
- **Отмена:** работа и новые принятия прекращаются, уже принятый код сохраняется. Необходимый
  откат или отключение оформляется отдельной задачей, а не выполняется слепым возвратом истории.

## Распределённая координация и recovery

- Единственный постоянный `agentd` не допускается. Один кластер координации соответствует одному
  meshbus realm; связь идёт через существующий RNS. Общий realm переиспользуется, право голоса
  ограничено зарегистрированными identity физических нод.
- Все доверенные физические ноды участвуют в голосовании. Исходный состав одинаково задан
  списком identity в конфигурации; состав после bootstrap изменяется согласованно, а не
  пересоздаётся по списку видимых сейчас peers.
- Новая разрешённая нода догоняет состояние и включается безопасным изменением состава.
  Длительно недоступная может быть автоматически исключена текущим большинством. Порог и
  процедура исключения пока не определены; без большинства новый состав не создаётся.
- Кластер может начинаться с одной ноды: из одной нужна одна, из двух нужны обе, из трёх — две.
  Без большинства новые согласуемые операции ждут.
- `agentd` прекращает продление r1s run, потеряв подтверждённое право сопровождать его. При
  отсутствии продлений работающий `r1sd` останавливает контейнер существующим runtime lease;
  второй lease контейнера в Lattice не вводится. Передача права должна учитывать последнее
  возможное продление, задержку остановки и восстановление `r1sd` после сбоя.
- Задачи, рабочие ветки и память позволяют повторно обнаружить и продолжить незавершённую
  работу. Реестр текущих контейнеров/ACP-сессий не становится долговременным состоянием задач.
  Необходимое служебное состояние самого протокола консенсуса проектируется отдельно.
- На каждой физической ноде свой сервис принятия, но принятый `main` един. F23 согласует
  переход от ожидаемого SHA к точному итоговому SHA до окончательного принятия; копии могут
  отставать, но не принимать другую вершину. Без большинства принятия ждут. Устаревший кандидат
  переносится на новый trunk, конфликт возвращается агенту с повторным review/checks исправлений.
  Radicle используется только как репликация; общий remote не считается атомарным приёмником.
  Доступность Git-объектов и recovery после решения до локального обновления ref требуют PoC.

## Открытые решения и порядок реализации

1. Завершить и подтвердить runtime-возможности [F19](./f19-agent-execution-loop/README.md), не
   подменяя ими будущие acceptance review и принятия.
2. В F22 проверить готовый Gerrit против небольшого Git-only `merged`: review/credentials,
   отдельные обновления состояния, exact-candidate checks, squash/rebase и recovery. Gerrit
   проверяется первым, но до ADR не выбран и не развёрнут. Собственный сервис рассматривается
   при несоответствии требованиям или чрезмерной сложности адаптации; отдельный multi-site стек
   не обязателен.
3. В F23 выбрать готовую основу консенсуса с RNS transport, storage/recovery, membership,
   передачей прав исполнения и межнодовым принятием trunk. Не писать собственный консенсус
   только ради хранения текущих запусков.
4. В F20 определить новый контракт и миграцию текущего `taskd`-reconciler к локальному CLI;
   в F21 связать готовые задачи с распределённым исполнением, review и эскалацией.

Итоговая приёмка включает фичу с несколькими задачами, docs и независимым review, конфликт
публикации, повторное review изменённого кандидата, потерю/возвращение ноды, потерю большинства,
перезапуски, восстановление драфта, паузу/отмену и удаление только успешно принятой фичи.
Конкретные протоколы, schema и deployment выбранного Git review backend фиксируются после PoC
в соответствующих фичах; незакрытые вопросы перечислены также в [BACKLOG.md](./BACKLOG.md).
