# Верхнеуровневый план Lattice

Это самый простой слой роадмапа: только куда мы идём и в каком порядке — без технических
деталей. Детали по фичам — в [`features/`](features/README.md), по задачам — в
[`tasks/`](features/README.md).

## К чему мы идём

Lattice — это децентрализованная сеть равноправных узлов. Каждый узел:

- полностью описан в Git и воспроизводится с нуля на чистом железе;
- сам подтягивает свой конфиг и обновляется без администратора;
- виден другим узлам через Reticulum независимо от физического транспорта;
- несёт полезную нагрузку: сервисы, реплику кода, вычисления, хранилище, шлюзы;
- служит воспроизводимой средой разработки с единым agent runtime для интерактивной работы и
  disposable workers;
- доступен администратору через rnsh без белого IP и проброса портов.

Сеть достигла цели, когда:

1. Новый узел разворачивает по документации человек, не участвовавший в разработке.
2. Потеря любого одного узла не мешает остальным обновляться и общаться.
3. Ни один секрет не лежит в репозитории открыто, а узел ставится без ручного копирования
   файлов сверх одного ключа.
4. Смена транспорта (радио-линк, отключение интернета) не требует правок в сервисах — только
   в слое интерфейсов Reticulum.
5. Задача разработки восстанавливается из состояния репозитория, спецификации задачи и явно
   сохранённых результатов, а потеря worker или cache не уничтожает ценное состояние.

## Масштаб

- **Ближний** — доверенный круг: единицы узлов, все известны лично, конфиги в этом репозитории.
- **Дальний** — внешний узел из чужого репозитория подключается без раскрытия внутренних секретов.

## Транспорт

Reticulum закладывается сразу поверх TCP/IP — интернет это первый интерфейс, а не отдельный
этап. Радио (LoRa/RNode) добавляется позже как ещё один интерфейс к уже работающей сети.

## Вехи и зависимости (без деталей)

| Веха | Зависит от | Смысл | Готово, когда | Фича |
| ---- | ---------- | ----- | ------------- | ---- |
| **1. Одна железная нода** | — | проект перестаёт быть только проектом | нода ставится с нуля по документации, переживает перезагрузку и сама применяет коммит из `main` | [F1](f1-one-node/README.md) |
| **2. Секреты и идентичность** | F1 | безопасность на ключах, а не на закрытости | репозиторий можно опубликовать целиком — доступа к узлам он не даёт | [F2](f2-secrets-identity/README.md) |
| **3. Reticulum поверх TCP/IP** | F1, F2 | узлы связываются по интернету, не только в LAN | с ноутбука открывается shell на узле за NAT через rnsh, связь переживает смену IP | [F3](f3-reticulum-tcp/README.md) |
| **4. Полезная нагрузка** | F1, F2 | нода становится self-hosted средой и source origin | конфиг распространяется без GitHub; на ноде работает прикладной сервис | [F4](f4-payload/README.md) |
| **5. Внешние узлы** | F2, F3, F4 | чистая граница узла и политика доверия | узел из внешнего репозитория участвует в сети без доступа к чужим секретам | [F5](f5-external-nodes/README.md) |
| **6. Радио и mesh** | F3 | работа на узком канале | два узла обмениваются данными по радио при отключённом интернете | [F6](f6-radio-mesh/README.md) |
| **7. LLM gateway** | F1, F2 | единая точка доступа к моделям и provider credentials | клиенты используют только логические классы моделей, а отказ upstream обрабатывается заданной политикой | [F7](f7-llm-gateway/README.md) |
| **8. Интерактивный Pi** | F7 | основной harness работает непосредственно на ноде | Pi TUI выполняет реальную задачу через gateway и воспроизводимый набор tools | [F8](f8-pi-runtime/README.md) |
| **9. Caches и artifacts** | F4-01, F7, F8 | ускорение отделено от ценного результата | caches можно удалить без потери корректности, artifacts сохраняются отдельно | [F9](f9-cache-artifact-plane/README.md) |
| **10. Disposable worker** | F8, F9 | задача выполняется в одноразовом окружении | полный цикл завершается результатом после уничтожения worker | [F10](f10-disposable-worker/README.md) |
| **11. Controller** | F10 | автоматизация очереди и жизненного цикла workers | задача переживает сбой controller/worker без потери или двойной публикации результата | [F11](f11-controller/README.md) |

Номера фич — стабильные идентификаторы, а не требование выполнять все строки сверху вниз.
Основной ближайший маршрут после F3:

```text
F4 source bootstrap
  → F7 LLM gateway
  → F8 Pi TUI
  → F9 cache/artifact plane
  → F10 disposable worker
  → F11 controller
```

F5 (внешние узлы) и F6 (радио) — независимые ветки расширения сети.

## Инварианты

Правила, которые не нарушаются ради скорости:

- **Слои не протекают**: `hardware` не знает о сети, `modules` не знают об инфраструктуре,
  инфраструктурные дефолты только в `profiles`, конкретика узла только в `nodes`.
- **Нет обязательного центра**: любой сервис-точка отказа либо дублируется, либо описывается,
  как сеть работает без него.
- **Деплой pull-based**: узел сам решает, когда обновиться; push — аварийный инструмент.
- **Конфигурация публична, секреты — нет**: безопасность держится на ключах.
- **Provider-agnostic agents**: Pi, workers и task definitions используют только логические
  классы `stupid` и `standard`; реальные модели и credentials остаются в
  LLM gateway.
- **Ценное состояние отделено от исполнения**: source/config/tasks/migrations — в Git/Radicle,
  секреты — в agenix, состояние оркестрации — в controller storage, artifacts — в object storage.
  Workers, workspaces и caches считаются disposable.
- **Shared filesystem не является скрытой зависимостью**: workers не требуют общей persistent
  POSIX FS; S3 используется для естественно объектных и неизменяемых результатов, а не через
  FUSE как рабочая директория.
- **Каждый этап заканчивается работающим состоянием**: сеть не остаётся в промежутке между
  заходами.

## Работа рывками

Проект развивается неравномерно, состояние должно восстанавливаться за один заход:

- Этап закрыт только после обновления README затронутых слоёв.
- Незавершённая работа фиксируется в [`BACKLOG.md`](./BACKLOG.md), а не остаётся в голове.
- Ветка `main` всегда собирается: узлы тянут из неё автоматически.
