# Определить точку входа Reticulum и как узел узнаёт её адрес

Фича: [F3 — Reticulum поверх TCP/IP](../features/f3-reticulum-tcp.md).

## Контекст

Для связи через интернет нужна точка входа: какой узел её обеспечивает на старте и как остальные
узлы получают её адрес. Это базовое решение, от которого зависят остальные TCP-задачи F3.

## Что сделать

- [x] Выбрать узлы-точки входа на старте сети.
- [x] Описать, как остальные узлы получают адрес точки входа (статически в конфиге или через
      механизм обнаружения).
- [x] Зафиксировать топологию в `ARCHITECTURE.md` (или в открытые решения, если ответ не готов).

## Критерий готовности

- [x] Точка входа определена, и адрес передаётся остальным узлам без ручных действий на каждом.

## Результат на 2026-09-04

Выбраны два публичных transport-узла: `sydney.reticulum.au:4242` и
`node.reticulumnet.nl:4242`. Собственный сервер не требуется. Общий реестр
`profiles/networking/reticulum.nix` передаёт адреса клиентам через flake/`comin`.
Профиль `profiles/rns-network` создаёт исходящие TCPClientInterface без LAN discovery,
входящего listener и HTTP control plane. Права rnsh задаются отдельно.

NixOS evaluation и независимый ConfigObj parser проверяют публичный реестр, его замену,
отключённый peer, IPv6, отсутствие входящих портов и неверные настройки.
На Mac закреплённый `rns-rs` получил анонсы и маршруты через эти peers. Для его shared instance
потребовался Darwin-патч; установленный Python RNS 1.5.2 также подтвердил Up у обоих peers
и маршруты через каждый из них. Linux/rnsh и смена сети клиента впоследствии проверены в F3-04;
F3-03 закрыта как отменённая, поскольку второй постоянной ноды в актуальном плане нет.
