# Проверить доступ по rnsh к узлу за NAT

Фича: [F3 — Reticulum поверх TCP/IP](../features/f3-reticulum-tcp.md).

## Контекст

Ключевой результат F3: с ноутбука через rnsh открывается shell на узле, который находится за
NAT (без белого IP), и связь переживает смену IP на стороне клиента.

## Что сделать

- [x] С ноутбука открыть shell на узле за NAT через rnsh по RNS-адресу.
- [ ] Сменить IP на стороне клиента и убедиться, что rnsh-сессия/восстановление работает.
- [x] Зафиксировать, какой транспорт и точка входа обеспечивают связь (см. f3-02).

## Критерий готовности

- [x] Shell на узле за NAT доступен через rnsh без белого IP и без проброса портов.
- [ ] Связь переживает смену IP на клиенте.

## Затрагиваемые файлы / слои

- `profiles/rnsh`
- `nodes/` (узлы сети)

## Результат на 2026-09-04

Python rnsh/RNS 1.5.2 на Mac выполнил `hostname` на homelab, где работают Rust rnsh и
rns-server из закреплённого snapshot. Destination `4cf57c92d739f498d2d007b79da66624`
проверен через доверенный SSH-канал. Разрешённая identity аутентифицируется; другая получает
`Identity is not allowed`. Адрес сохранился после перезапуска, файл identity имеет права
`0600` и находится на persistent mount.

Используются исходящие TCP uplink к Sydney/ReticulumNet, AutoInterface отсутствует. На homelab
внешний firewall открывает только порт 22; доступ rnsh не использует SSH или LAN discovery.
Mac и homelab находились в одной LAN, но RNS-путь проходил через публичный gateway.
Проверка клиента из другой сети и фактическая смена его IP ещё не выполнены.

В процессе найден и исправлен сбой последнего шага доставки HEADER_1 в shared daemon `rns-rs`.
Патч и регрессионный тест включены в пакет сервера; все 656 тестов `rns-core` прошли на macOS
и в Linux-сборке. Диагностические Python-сервисы на homelab остановлены, runtime override удалены.

Проверены отдельные подключения клиента: только Sydney и только ReticulumNet (второй uplink
отключён, использован отдельный пустой каталог состояния). В обоих случаях rnsh установил
соединение; через ReticulumNet открыт интерактивный bash. Это проверка резервных путей,
а не обещание переноса уже открытой сессии при смене IP.

Ограничение, найденное при финальной проверке: быстрое выполнение нескольких команд с `exit`
привело к `RNS send failed` и завершению процесса rnsh. Systemd перезапустил listener через
5 секунд; следующий интерактивный вход тем же ключом и с прежним destination прошёл.
Это не считается бесшовным восстановлением: нужно обработать ошибку закрытой сессии локально,
не завершая весь listener, и проверить сохранение остальных сессий.

## Исправление ошибки закрытия сессии (история)

До слияния upstream в пакет rnsh был добавлен `rnsh-session-send.patch`. Обработчик событий процесса проверяет,
что сессия ещё существует и выполняет команду. При ошибке отправки удаляется только эта
сессия; работающий дочерний процесс завершается, link закрывается. При событии `ProcessExited`
процесс уже собран waiter-потоком, поэтому сигнал по его PID не отправляется.
Запоздавшие события удалённой сессии игнорируются. Ошибки EOF и `CommandExited` также
не выходят из общего цикла listener.

В Nix-сборку включены 29 unit-тестов rnsh. Три новые регрессии проверяют события после
`LinkClosed`, ошибки отправки вывода/EOF/exit status с сохранением соседней сессии,
и штатную доставку вывода, EOF и кода завершения. На macOS и Linux все 29 тестов прошли;
вычисление flake для всех систем также прошло. Для Linux sandbox путь `/bin/cat` в upstream-тесте
заменён на `cat` из Nix store; тесты не исключались.

На homelab проверены две одновременные авторизованные сессии через отдельный Python RNS daemon
на Mac. Быстрая отправка `id`, `hostname`, `exit` вызвала ошибку отправки в первой сессии.
Она закрылась, а вторая после этого успешно выполнила `hostname` и `id`.
PID listener остался `30369`, `NRestarts=0`. Ошибка теперь записывается в logfile с ID
затронутого link и не завершает listener. Новая сессия после сбоя также подключилась
с прежней identity и выполнила `hostname`.

После патча изоляции оставалось ограничение: быстрый вывод мог вызвать ошибку отправки ещё
до `exit` и оборвать собственную сессию. В повторном тесте 2026-09-04 в 13:47:59 UTC с `rnsh -v`
подтверждён `Channel send failed: NotReady`, непосредственно перед закрытием сессии.
`Channel::send` возвращает эту ошибку при заполненном окне отправки, а
`RnsNode::send_channel_message` теряет её тип, преобразуя в общий `SendError`.
Потребовались ожидание готовности канала и очередь отправки: один патч изоляции не обеспечивал
доставку всего вывода.

Проверенный патч, результаты 29 тестов на каждой платформе и проверки соседней сессии
опубликованы в [комментарии к #140](https://github.com/lelloman/rns-rs/issues/140#issuecomment-5541414152).
Отдельный дефект обработки заполненного окна вынесен в
[#141](https://github.com/lelloman/rns-rs/issues/141). Временный runtime override после тестов
удалён, тестовый клиентский daemon остановлен; на homelab снова работает конфигурация `e934ee9`.

## Очередь вывода при NotReady (история)

До слияния upstream `rnsh-backpressure.patch` применялся после патча изоляции. Новый API
`RnsNode::try_send_channel_message` различает временный `NotReady` и постоянные ошибки;
старый метод сохраняет прежнюю сигнатуру. Вывод listener помещается в очередь сессии
и повторяется при освобождении окна. Idle ticks раз в 100 мс продолжают доставку после
завершения дочернего процесса; сессия удаляется только после принятия channel-слоем EOF
и `CommandExited`, поставленных за последним выводом. Разрыв link удаляет очередь.

В первоначальной версии очередь ограничивалась 1 МиБ encoded payload и 4096 сообщениями,
а переполнение закрывало сессию. В правке `a8408b6` эти пороги удалены для соответствия
Python rnsh: накопленный вывод ждёт освобождения окна. Flush остаётся ограничен 16
сообщениями для обслуживания других сессий. Канал событий от reader-потоков остаётся
неограниченным; буферизация stdin клиента этим патчем не меняется.

Все 34 unit-теста rnsh прошли на macOS и Linux. Новые тесты используют настоящий
`Channel` с окном в один пакет: проверяют ожидание ACK, отсутствие дубликатов, порядок
stdout/stderr/EOF/exit status, независимость второй сессии, лимиты очереди и разрыв link.
`nix flake check --all-systems --no-build` также прошёл.

На homelab две авторизованные Python rnsh-сессии работали через общий тестовый daemon Mac
и публичные TCP uplink. `seq 1 4000` передал ровно 4000 строк / 18 893 байта без потерь
и дубликатов. Затем в ту же сессию одним вводом отправлены `id`, `hostname`, `exit 17`;
с `--mirror` клиент вернул 17. Вторая сессия отвечала во время передачи и после завершения
первой, затем вернула 0. В ходе успешного теста фиксировался `NotReady`; PID listener
остался `46340`, `NRestarts=0`, failed units отсутствовали.

Совмещённый патч против `cb257acf` и результаты опубликованы в
[#141](https://github.com/lelloman/rns-rs/issues/141#issuecomment-5541627213).
После проверки runtime override удалён и тестовый daemon остановлен; постоянное
развёртывание патча не выполнялось. Проверка смены IP клиента по-прежнему остаётся открытой.

## Upstream PR

По приглашению автора создан форк `mytecor/rns-rs` и открыт
[PR #142](https://github.com/lelloman/rns-rs/pull/142) в `lelloman/rns-rs:master`,
связывающий исправления с #140 и #141. Ветка `fix/rnsh-session-backpressure` основана
на том же `cb257acf`; первый commit PR — `2c4c8a3495d1f9b1044cf0e33691204069022512`.

На самой ветке PR с Rust 1.96.0/macOS напрямую прошли 34 теста rnsh и `cargo fmt --check`.
Для этого включены исправления типов указателей `openpty` и аргумента `ioctl`, ранее
применявшиеся в Nix. Clippy для библиотеки `rns-net` и библиотеки/тестов `rns-cli` прошёл
с разрешением существующих macOS-предупреждений `unused_variables` и исключениями upstream.
Полный Linux-набор оставлен CI upstream; ограничение существующих Linux-зависимых
тестов `rns-net` на macOS указано в описании PR.

После сравнения с Python добавлен минимальный follow-up `a8408b6`: удалены только
разрыв по размеру очереди и его счётчики. Вместо тестов лимита проверяется сохранение
более 1 МиБ / 4096 сообщений при заполненном окне, включая EOF и exit status;
соседняя сессия продолжает работать. Все 34 теста, форматирование и Clippy для rnsh
прошли на Rust 1.96/macOS. Патч Nix синхронизирован с веткой PR и проверен на применение;
Linux-сборка и сетевой тест для этой узкой правки повторно не запускались.

PR #142 слит в `master` 2026-09-04. Lattice обновлён на merge-коммит
`042e37047b70ea0e06b9aff0aed6214bc305ab35`, который одновременно был последним commit
upstream на момент обновления. Оба локальных rnsh-патча и Nix-подстановки типов libc удалены;
серверные патчи, не входившие в PR, сохранены.
После обновления `rnsh` собран и прошёл 34 теста на macOS и x86_64 Linux;
`rns-server` собран на macOS и прошёл 656 тестов `rns-core`. Оба бинарника выводят
короткую ревизию `042e37047b70` в `--version`.
