# Проверить доступ по rnsh к узлу за NAT

Фича: [F3 — Reticulum поверх TCP/IP](../features/f3-reticulum-tcp.md).

## Контекст

Ключевой результат F3: с ноутбука через rnsh открывается shell на узле, который находится за
NAT (без белого IP), и связь переживает смену IP на стороне клиента.

## Что сделать

- [x] С ноутбука открыть shell на узле за NAT через rnsh по RNS-адресу.
- [ ] Сменить IP на стороне клиента и убедиться, что rnsh-сессия/восстановление работает.
- [x] Зафиксировать, какой транспорт и точка входа обеспечивают связь (см. f3-02).

## Критерий готовности

- [x] Shell на узле за NAT доступен через rnsh без белого IP и без проброса портов.
- [ ] Связь переживает смену IP на клиенте.

## Затрагиваемые файлы / слои

- `profiles/rnsh`
- `nodes/` (узлы сети)

## Результат на 2026-09-04

Python rnsh/RNS 1.5.2 на Mac выполнил `hostname` на homelab, где работают Rust rnsh и
rns-server из закреплённого snapshot. Destination `4cf57c92d739f498d2d007b79da66624`
проверен через доверенный SSH-канал. Разрешённая identity аутентифицируется; другая получает
`Identity is not allowed`. Адрес сохранился после перезапуска, файл identity имеет права
`0600` и находится на persistent mount.

Используются исходящие TCP uplink к Sydney/ReticulumNet, AutoInterface отсутствует. На homelab
внешний firewall открывает только порт 22; доступ rnsh не использует SSH или LAN discovery.
Mac и homelab находились в одной LAN, но RNS-путь проходил через публичный gateway.
Проверка клиента из другой сети и фактическая смена его IP ещё не выполнены.

В процессе найден и исправлен сбой последнего шага доставки HEADER_1 в shared daemon `rns-rs`.
Патч и регрессионный тест включены в пакет сервера; все 656 тестов `rns-core` прошли на macOS
и в Linux-сборке. Диагностические Python-сервисы на homelab остановлены, runtime override удалены.

Проверены отдельные подключения клиента: только Sydney и только ReticulumNet (второй uplink
отключён, использован отдельный пустой каталог состояния). В обоих случаях rnsh установил
соединение; через ReticulumNet открыт интерактивный bash. Это проверка резервных путей,
а не обещание переноса уже открытой сессии при смене IP.

Ограничение, найденное при финальной проверке: быстрое выполнение нескольких команд с `exit`
привело к `RNS send failed` и завершению процесса rnsh. Systemd перезапустил listener через
5 секунд; следующий интерактивный вход тем же ключом и с прежним destination прошёл.
Это не считается бесшовным восстановлением: нужно обработать ошибку закрытой сессии локально,
не завершая весь listener, и проверить сохранение остальных сессий.

## Проверка после загрузки конфигурации e934ee9

2026-09-04 подтверждена загрузка homelab в Generation 7, установленную через `comin`.
Boot ID изменился с `4833bf04-bacb-4c25-9224-8caf282230b1` на
`da0e8a72-dfe0-4929-9deb-4edacbd4115a`; выбранная загрузочная запись и
`/run/current-system` соответствуют новой конфигурации. В initrd создан новый `@root`.

Wi-Fi подключился автоматически, SSH доступен по прежнему доверенному host key,
оба исходящих TCP uplink восстановились. Секреты agenix присутствуют после загрузки
(содержимое при проверке не выводилось). Каталоги `/var/lib/rns` и `/var/lib/rnsh`
смонтированы из `@persist`; identity слушателя принадлежит `rnsh:rnsh` с правами `0600`.

Python rnsh на Mac подключился с прежней операторской identity к прежнему destination
`4cf57c92d739f498d2d007b79da66624`. Через shell выполнены `hostname`, `id` и чтение boot ID:
получены `mytecor-homelab`, пользователь `rnsh` и тот же новый boot ID, что через SSH.
Это подтверждает доступ после перезагрузки сервера; смена IP клиента остаётся непроверенной.

[CI для e934ee9](https://github.com/mytecor/lattice/actions/runs/33875721086) завершился успешно.

При закрытии этой сессии повторился `RNS send failed`: listener завершился с кодом 1,
systemd восстановил его через 5 секунд с прежним destination. Это повторное воспроизведение
[issue #140](https://github.com/lelloman/rns-rs/issues/140), а не сбой загрузки или потеря identity.

## Исправление ошибки закрытия сессии

В пакет rnsh добавлен `rnsh-session-send.patch`. Обработчик событий процесса проверяет,
что сессия ещё существует и выполняет команду. При ошибке отправки удаляется только эта
сессия; работающий дочерний процесс завершается, link закрывается. При событии `ProcessExited`
процесс уже собран waiter-потоком, поэтому сигнал по его PID не отправляется.
Запоздавшие события удалённой сессии игнорируются. Ошибки EOF и `CommandExited` также
не выходят из общего цикла listener.

В Nix-сборку включены 29 unit-тестов rnsh. Три новые регрессии проверяют события после
`LinkClosed`, ошибки отправки вывода/EOF/exit status с сохранением соседней сессии,
и штатную доставку вывода, EOF и кода завершения. На macOS и Linux все 29 тестов прошли;
вычисление flake для всех систем также прошло. Для Linux sandbox путь `/bin/cat` в upstream-тесте
заменён на `cat` из Nix store; тесты не исключались.

На homelab проверены две одновременные авторизованные сессии через отдельный Python RNS daemon
на Mac. Быстрая отправка `id`, `hostname`, `exit` вызвала ошибку отправки в первой сессии.
Она закрылась, а вторая после этого успешно выполнила `hostname` и `id`.
PID listener остался `30369`, `NRestarts=0`. Ошибка теперь записывается в logfile с ID
затронутого link и не завершает listener. Новая сессия после сбоя также подключилась
с прежней identity и выполнила `hostname`.

Остаётся отдельное ограничение: быстрый вывод может вызвать ошибку отправки ещё до `exit`
и оборвать собственную сессию. В повторном тесте 2026-09-04 в 13:47:59 UTC с `rnsh -v`
подтверждён `Channel send failed: NotReady`, непосредственно перед закрытием сессии.
`Channel::send` возвращает эту ошибку при заполненном окне отправки, а
`RnsNode::send_channel_message` теряет её тип, преобразуя в общий `SendError`.
Нужны ожидание готовности канала и очередь отправки. Патч изолирует ошибку, но не обеспечивает
доставку всего вывода и не считается бесшовным восстановлением сессии.

Проверенный патч, результаты 29 тестов на каждой платформе и проверки соседней сессии
опубликованы в [комментарии к #140](https://github.com/lelloman/rns-rs/issues/140#issuecomment-5541414152).
Отдельный дефект обработки заполненного окна вынесен в
[#141](https://github.com/lelloman/rns-rs/issues/141). Временный runtime override после тестов
удалён, тестовый клиентский daemon остановлен; на homelab снова работает конфигурация `e934ee9`.
