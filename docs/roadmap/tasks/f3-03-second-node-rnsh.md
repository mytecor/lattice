# Поднять второй узел; включить `profiles/rnsh` на обоих

Фича: [F3 — Reticulum поверх TCP/IP](../features/f3-reticulum-tcp.md).

## Контекст

Для того чтобы проверить межузловую связь, нужен второй узел, и на обоих узлах должен работать
`profiles/rnsh` (listener remote shell через Reticulum).

## Что сделать

- [ ] Создать второй узел по образцу `nodes/example`.
- [ ] Включить `profiles/rnsh` на обоих узлах.
- [ ] Подключить TCP-интерфейсы ([f3-01](./f3-01-reticulum-tcp-interfaces.md)) на обоих.
- [ ] Проверить, что оба узла видят друг друга через Reticulum.

## Критерий готовности

- [x] Два узла обмениваются данными через Reticulum поверх TCP/IP.
- [ ] `rnsh`-listener активен на обоих.

## Затрагиваемые файлы / слои

- `nodes/` (второй узел, новый)
- `profiles/rnsh`
- `profiles/rns-server`

## Промежуточный результат на 2026-09-04

Homelab подключён к Sydney/ReticulumNet и запускает rnsh от отдельного пользователя с явным
allowlist. Mac с Python RNS 1.5.2 выступает вторым тестовым участником: команда `hostname`
выполняется на homelab через публичный маршрут. Чужая identity получает явный отказ.
`/var/lib/rns` и `/var/lib/rnsh` сохранены в `/persist`; destination слушателя не менялся
при повторных активациях/перезапусках.

Постоянная вторая NixOS-нода в `nodes/` пока не создана, listener на Mac не включался.
Поэтому задача остаётся открытой, несмотря на выполненную межузловую проверку.
