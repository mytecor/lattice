# Роадмап Lattice

Документ описывает целевое состояние сети и путь к нему. Он отвечает на вопрос "к чему мы идем",
а не "как устроен код" - для второго есть [ARCHITECTURE.md](./ARCHITECTURE.md).

## Целевое состояние

Lattice - это набор равноправных узлов, каждый из которых:

- полностью описан в Git и воспроизводим с нуля на чистом железе;
- сам подтягивает свою конфигурацию и обновляется без участия администратора;
- виден остальным узлам через Reticulum независимо от того, какой физический транспорт под ним;
- несет полезную нагрузку: сервисы владельца, реплику кода, вычисления и хранилище, шлюзы наружу;
- доступен администратору через rnsh без белого IP и без проброса портов.

Сеть считается достигшей цели, когда:

1. Новый узел разворачивается по документации человеком, который не участвовал в разработке.
2. Потеря любого одного узла не мешает остальным обновляться и общаться между собой.
3. Ни один секрет не лежит в репозитории в открытом виде, при этом узел ставится с нуля без ручного
   копирования файлов сверх одного ключа.
4. Смена транспорта (добавление радио-линка, отключение интернета на узле) не требует правок в
   конфигурации сервисов - только в слое интерфейсов Reticulum.

### Масштаб

Ближняя цель - доверенный круг: единицы узлов, все известны лично, конфигурации живут в этом
репозитории. Дальняя - возможность подключить внешний узел, конфигурация которого лежит в чужом
репозитории, без раскрытия ему внутренних секретов сети.

### Транспорт

Reticulum закладывается сразу, поверх TCP/IP. Отдельного этапа "сначала VPN, потом RNS" нет:
интернет - это первый интерфейс Reticulum, а не отдельный уровень со своей адресацией. Радио
(LoRa/RNode) добавляется позже как еще один интерфейс к уже работающей сети.

## Инварианты

Правила, которые не нарушаются ради скорости. Если шаг требует нарушить инвариант - это сигнал, что
шаг спроектирован неверно.

- **Слои не протекают.** `hardware` не знает о сети, `modules` не знают об инфраструктуре Lattice,
  инфраструктурные дефолты живут только в `profiles`, конкретика узла - только в `nodes`.
- **Нет обязательного центра.** Любой сервис, который становится единственной точкой отказа
  (координатор VPN, единственный seed, единственный gitops-remote), либо дублируется, либо
  сопровождается описанием, как сеть работает без него.
- **Деплой pull-based.** Узел сам решает, когда обновиться (`comin`). Push через `nixos-rebuild
  --target-host` остается аварийным инструментом, а не основным путем.
- **Конфигурация публична, секреты - нет.** Репозиторий можно показать постороннему; безопасность
  держится на ключах, а не на закрытости конфигов.
- **Каждый этап заканчивается работающим состоянием.** Работа идет рывками, поэтому недопустимо
  оставлять сеть в промежуточном состоянии между заходами.

## Что уже есть

- Слоистая структура каталогов и README для каждого слоя.
- `hardware/intel-n100`, `modules/{ephemeral-root,rns-server,rnsh,wireless}`,
  `profiles/{gitops,networking,radicle,rns-server,rnsh,tcp-gateway}`, `packages/rns-rs`.
- Typed-генерация конфигов Reticulum в `modules/rns-server`.
- Ephemeral root на Btrfs + impermanence.
- `profiles/gitops` с `comin`, нацеленным на GitHub и на локальный путь Radicle-хранилища.
- `nodes/example` как шаблон узла.

Известные расхождения с документацией, которые нужно закрыть до вехи 1:

- `modules/README.md` и `profiles/README.md` описывают каждый каталог как самостоятельный flake с
  `nixosModule`, но на диске лежат только `config.nix`/`options.nix`, а `nodes/example` подключает их
  как `flake = false` пути. Нужно выбрать одну модель и привести к ней и код, и доки.
- `profiles/base`, упомянутый в README и в DEPLOYMENT.md, не существует.
- `profiles/rns-server` поднимает только `AutoInterface` со `discovery_scope = "link"`, то есть
  работает исключительно внутри одного broadcast-домена. Межузловой связи пока нет.
- В `nodes/example/flake.nix` секция profiles закомментирована: ни один профиль реально не собирается.
- Секреты - заглушки: `dummy-key-for-vm` в radicle, `fakeWirelessSecret` в конфиге узла.

## Этапы

Этапы упорядочены по зависимостям, а не по календарю. Каждый заканчивается проверяемым критерием.

### Этап 1. Одна железная нода в работе

Первая веха: проект перестает быть только проектом.

Задачи:

- Собрать `profiles/base` и подключить его в `nodes/example` (или в первый реальный узел), чтобы
  профили действительно попадали в сборку.
- Привести модель flake/не-flake для `modules` и `profiles` к одному решению, обновить README.
- Развернуть первый узел на Intel N100 с нуля по DEPLOYMENT.md, зафиксировав все ручные шаги,
  которых не хватило в документации.
- Убедиться, что `comin` тянет из GitHub и применяет конфиг узла.

Критерий готовности: узел установлен с нуля по документации, переживает перезагрузку и
самостоятельно применяет коммит из `main` без участия администратора.

Осознанно откладываем: вторую ноду, radicle-remote в comin, реальные секреты.

### Этап 2. Reticulum поверх TCP/IP и удаленный доступ

Задачи:

- Добавить в `modules/rns-server` и `profiles/rns-server` описание TCP-интерфейсов Reticulum
  (клиентские и серверные), чтобы узлы связывались через интернет, а не только внутри LAN.
- Определить, какой узел выступает точкой входа на старте, и как остальные узлы получают его адрес.
- Поднять второй узел; включить `profiles/rnsh` на обоих.
- Проверить связь и админ-доступ по RNS-адресу без белого IP на клиентской стороне.

Критерий готовности: с ноутбука через rnsh открывается shell на узле, который находится за NAT, и
эта связь переживает смену IP на стороне клиента.

Открытые вопросы этапа: нужен ли резервный транспорт (Yggdrasil/I2P) как дополнительный интерфейс
Reticulum, или достаточно нескольких TCP-точек входа.

### Этап 3. Секреты и идентичность узла

Задачи:

- Ввести sops-nix или agenix; выбрать одно и зафиксировать выбор в ARCHITECTURE.md.
- Определить, что является идентичностью узла: отдельные ключи на каждую подсистему или один
  host-ключ, из которого выводятся остальные.
- Описать процедуру bootstrap: как ключ попадает на узел при первой установке.
- Заменить `dummy-key-for-vm` и `fakeWirelessSecret` на реальную схему; в `nodes/example` оставить
  заведомо тестовые значения с явной пометкой.
- Описать процедуру ротации и отзыва ключа скомпрометированного узла.

Критерий готовности: репозиторий можно опубликовать целиком, и это не дает доступа ни к одному узлу.

### Этап 4. Полезная нагрузка

Узел перестает быть только участником сети.

Задачи:

- Radicle-seed на нескольких узлах; переключить `comin` на radicle-remote как основной источник, а
  GitHub оставить зеркалом. Отдельно решить проблему первичной загрузки: узел должен получить
  radicle-хранилище до того, как сможет тянуть из него конфиг.
- Профиль для прикладных сервисов владельца поверх `tcp-gateway`.
- Определить, что означает "общее хранилище и вычисления": какие узлы отдают ресурсы, кому и по
  какому протоколу. Сейчас это самая непроработанная часть цели.

Критерий готовности: конфигурация сети распространяется между узлами без GitHub, и на узлах работает
хотя бы один прикладной сервис, доступный через шлюз.

### Этап 5. Внешние узлы

Задачи:

- Вынести хотя бы один узел в отдельный репозиторий и подключить его в корневой flake как внешний
  input - проверить, что граница узла действительно чистая.
- Описать политику доверия: что дает подключение узла к сети, к чему он получает доступ, что
  происходит при исключении.
- Довести CONTRIBUTING.md до инструкции, по которой посторонний человек поднимает свой узел.

Критерий готовности: узел, конфигурация которого лежит вне этого репозитория, участвует в сети и не
имеет доступа к секретам других узлов.

### Этап 6. Радио и mesh

Задачи:

- Добавить интерфейсы RNode/LoRa в слой интерфейсов Reticulum.
- Проверить, что сервисы, написанные на этапах 2-4, работают на узком канале, и вынести в отдельный
  профиль то, что не работает.
- Довести идею из [MSG_BUS.md](./MSG_BUS.md) до модуля, если она к тому моменту еще нужна.

Критерий готовности: два узла обмениваются данными по радио при отключенном интернете.

## Открытые решения

Вопросы, которые сознательно не закрыты и ждут своего этапа:

1. Flake или простые модули для `modules/` и `profiles/` - блокирует этап 1.
2. Топология точек входа Reticulum: сколько узлов с публичным адресом и как они анонсируются - этап 2.
3. sops-nix или agenix; одна идентичность узла или несколько ключей - этап 3.
4. Bootstrap radicle: как узел получает хранилище, из которого потом сам обновляется - этап 4.
5. Что конкретно означает общий пул вычислений и хранилища - требует отдельного разбора до этапа 4.
6. Нужен ли резервный оверлей (Yggdrasil/I2P) или достаточно нескольких TCP-точек входа.

## Работа рывками

Проект развивается неравномерно, поэтому состояние должно восстанавливаться за один заход:

- Этап считается закрытым только после того, как обновлены README затронутых слоев.
- Незавершенная работа фиксируется здесь, в разделе открытых решений, а не остается в голове.
- Ветка `main` всегда собирается: узлы тянут из нее автоматически, и сломанный коммит ломает сеть.
